## 1. 文档目标

这份文档用于统一说明当前 `OpenClaw` 的安装与工作流部署基线。

重点不是重写安装脚本，而是明确：

- 安装入口是什么
- 安装脚本支持哪些参数
- 工作流是什么结构
- hooks 是什么结构
- jobs 是什么结构
- 飞书如何接入
- 记忆如何统一到 `OpenViking`
- `auto-evolution` 为什么必须启用

当前原则：

- 复用现有安装脚本，不重复发明第二套部署逻辑
- 支持 `Windows 本机` 和 `Linux 服务器`
- `Telegram` 与 `Feishu` 都纳入标准通道
- 记忆方案只保留 `OpenViking` 与官方内置能力，不再引入其他第三方记忆路线
- 明文 key 先不作为当前阶段阻塞项，优先快速上线，后续再治理

## 2. 标准安装入口

当前标准安装入口以仓库脚本为准：

- `scripts/openclaw-ops/install_workflow_profile.py`
- `setup.py`

推荐理解方式：

- `install_workflow_profile.py` 是实际安装与同步入口
- `setup.py` 是仓库层的统一入口封装

安装技能后续也应以这两个入口为基线，不再单独维护一套平行的“手工安装逻辑”。

## 3. 安装脚本参数说明

当前安装脚本不要求每次都传全量参数，但需要知道它支持哪些能力。

### 3.1 基础参数

- `--profile`
  - 安装档位，当前主要可理解为 `core` 或 `all`
- `--python-bin`
  - 指定 Python 解释器
- `--jobs-file`
  - 指定 jobs 配置来源
- `--openclaw-home`
  - 指定运行时目录
- `--workflow-repo-path`
  - 指向当前工作流仓库
- `--overlay-config-source`
  - 指定 overlay 配置来源

### 3.2 配置与运行时同步参数

- `--sync-overlay-config`
  - 将仓库里的 overlay 配置同步到运行时 `~/.openclaw/openclaw.json`
- `--ensure-runtime-skills`
  - 确保运行时技能被同步到位
- `--required-skills-manifest`
  - 指定技能清单
- `--reconcile-gateway-service`
  - 校准 gateway service
- `--gateway-service-prefer`
  - 指定倾向 `user` 或 `system`

### 3.3 工作流与任务中心参数

- `--project-registry`
  - 项目注册表
- `--task-db`
  - 任务中心数据库
- `--workflow-repo-id`
  - 当前工作流仓库标识

### 3.4 通知与投递参数

- `--channel`
  - 通知通道
- `--to`
  - 投递目标

### 3.5 定时任务与 job 频率参数

- `--todo-every-ms`
- `--task-executor-every-ms`
- `--project-index-every-ms`
- `--git-sync-every-ms`
- `--auto-update-install-every-ms`
- `--install-web-intel-jobs`
- `--install-multi-project-*`

### 3.6 执行模式参数

- `--dry-run`
  - 只演练，不真正写入
- `--emit-json`
  - 输出结构化结果，便于审计与自动化消费

## 4. 工作流结构说明

当前工作流不是“单 Agent 串行处理”，而是一套带任务中心、角色分工、验收闭环的结构。

### 4.1 入口与角色

当前推荐结构按四层理解：

- 入口层：`arbitrageagent`、`spreadagent` 两个 Hermes Discord profile。
- 工作流层：`/home/arbops/.local/bin/smart-arb-pipeline` 调用 `/home/arbops/.hermes/ops/pipeline_runner.py`。
- 逻辑 owner 层：`coordinator`、`project-agent`、`web-agent`、`reviewer`、`backend-dev`、`frontend-dev`、`tester`、`deployer`、`doc-writer`。
- 定时任务层：`ops-agent`、`project-agent`、`optimization-agent`。

### 4.2 任务模型

任务采用双池模型：

- `todo`
  - 延迟执行、低优先级、可批处理任务
- `jobs`
  - 立即执行、高优先级、阻断型任务

### 4.3 闭环要求

每条任务都应该有清晰闭环：

1. 需求
2. 结果
3. 验收阈值
4. 评分
5. 动作

动作结果通常是：

- 通过
- 重试
- 升级人工

## 5. Hooks 结构说明

hooks 分成两层：

- 工作流治理 hooks
- 自动进化 hooks

### 5.1 自动进化 hooks

自动进化不是可选项，当前基线中应视为强制启用。

强制启用的 hooks：

- `hardflow-experience-capture`
- `hardflow-experience-recall`
- `hardflow-experience-evolve`

它们对应的职责分别是：

- `capture`
  - 沉淀问题解决经验
- `recall`
  - 在后续执行中召回相关经验
- `evolve`
  - 对经验做合并、优化、进化

### 5.2 工作流治理 hooks

配套治理 hooks 包括：

- `hardflow-command-guard`
- `hardflow-audit`
- `hardflow-stop-gate-reminder`

这类 hooks 负责：

- 命令边界控制
- 操作审计
- stop gate 提醒

### 5.3 hooks 加载方式

推荐通过 `hooks.internal` 体系启用：

- 打开 `hooks.internal.enabled`
- 将 hooks 目录加入 `hooks.internal.load.extraDirs`
- 对每个 hook 单独设置 `enabled=true`

## 6. Jobs 结构说明

当前 jobs 的目标不是“堆定时任务”，而是把 workflow 的关键维护动作标准化。

现有 job 类型主要包括：

- `task-executor`
  - 执行任务中心里的待处理任务
- `git-sync`
  - 同步仓库状态
- `project-index`
  - 维护项目索引
- `reviewer-scan`
  - 做审查扫描
- `todo-patrol`
  - 巡检待办
- `governance-evolution`
  - 工作流治理与演进
- `web-intel`
  - 外部信息补充
- `auto-update-install`
  - 自动更新与重装维护

jobs 的核心不是名字，而是要做到：

- 能明确归属
- 能明确频率
- 能输出日志
- 能失败留痕
- 能被重新安装或回滚

## 7. 配置同步说明

当前配置同步以 overlay 模式为准。

仓库里的基线配置来源：

- `openclaw/openclaw.json`

安装脚本负责把这份 overlay 合并进运行时：

- `~/.openclaw/openclaw.json`

建议继续保持这种模式：

- 仓库保留基线
- 机器保留运行时最终态
- 通过安装脚本做同步

## 8. 通道说明

### 8.1 Telegram

`Telegram` 是当前默认标准通道之一。

建议保留：

- bot token
- `dmPolicy`
- `groupPolicy`
- 代理配置（如需要）

### 8.2 Feishu

`Feishu` 也是标准通道，应纳入统一部署基线。

当前接入方式：

## 9. 记忆方案说明

当前记忆路线统一为：

- 官方内置记忆能力
- `OpenViking`

其他第三方记忆路线不再继续扩展。

### 9.1 OpenViking

标准仓库：

- <https://github.com/volcengine/OpenViking>

定位：

- `OpenViking` 作为 AI Agent 的上下文数据库
- 用于统一管理 memory、resources、skills
- 作为当前记忆增强的标准后端

### 9.2 运行原则

推荐原则：

- 运行 `openviking-server`
- 通过本地 HTTP 服务提供记忆能力
- `OpenClaw` 侧通过 `memory-openviking` 接入
- 不再引入其他额外的第三方记忆插件路线

### 9.3 端口与环境

`OpenViking` 默认常见端口为：

- `127.0.0.1:1933`

如果本机端口冲突或权限受限，可以按机器实际情况调整，但必须在部署文档和运行时配置里同步说明。

## 10. auto-evolution 策略

这里单独强调：

- `auto-evolution` 不是可选
- 当前部署基线中视为强制启用

原因很明确：

- 没有自动进化，经验无法持续沉淀
- 没有召回链路，workflow 很难形成长期收益
- 没有周期维护，记忆会越来越脏，检索质量会下降

所以后续技能实现里应直接采用：

- 默认启用
- 部署后强校验
- 缺失时直接报出未完成项

## 11. 当前接受的上线取舍

为了快速上线，当前允许以下取舍：

- provider key 先允许保留在配置中
- 不把 secret 管理作为当前阶段阻塞项

但需要明确：

- 这只是阶段性取舍
- 后续仍应收敛到环境变量或 Secret 管理

## 12. 建议的标准部署顺序

推荐顺序如下：

1. 安装或更新 `OpenClaw`
2. 运行工作流安装脚本
3. 同步 overlay 配置
4. 安装 `Feishu` 插件
5. 配置 `Telegram + Feishu`
6. 部署并启动 `OpenViking`
7. 绑定 `memory-openviking`
8. 强制启用 `auto-evolution` hooks
9. 安装 jobs 与定时维护任务
10. 做状态检查与验收

## 13. 对后续技能的要求

后续如果建设 `openclaw-workflow-deploy` 技能，建议它只做三件事：

1. 调用现有安装脚本
2. 补齐平台差异说明
3. 输出部署结果与验收结论

不建议在技能里重新实现一套新的安装逻辑。
