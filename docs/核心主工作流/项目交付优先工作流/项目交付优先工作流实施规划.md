# 项目交付优先工作流 — 实施规划

> 版本：v0.1 | 2026-04-21
> 架构设计：[项目交付优先工作流架构设计.md](项目交付优先工作流架构设计.md)

## 1. 实施目标

把默认工作流从“自动进化优先”调整为“项目交付优先”，并把以下能力正式落地：

1. reviewer 前移到需求、方案、代码三个阶段。
2. project-agent 升级为项目维护 owner 和项目记忆 owner。
3. 新功能默认先查官方文档和成熟方案。
4. 第三方 API 更新变成项目维度的 watch，而不是全局乱扫。
5. 默认 cron/job 基线裁剪为项目交付核心链。

## 2. Phase 划分

### Phase 0：文档与事实源建立

目标：

1. 建立本目录三件套。
2. 更新 `docs/INDEX.md`、`docs/核心主工作流/README.md`、`docs/execution-roadmap.md`。
3. 在 `todo.md` / `done.md` 中记录本轮方向收口。

状态：✅ 本轮完成

### Phase 1：reviewer 前移改造

目标：

1. 把 reviewer 从单纯代码审查扩展为：
   - requirements review
   - solution review
   - code review
2. 为三种审查建立统一输出契约。
3. 让 reviewer 的问题能回写需求文档和实施规划，而不是只停留在评论层。

实施步骤：

1. 梳理现有 reviewer prompt、skills、runner 和 gate 入口。
2. 为需求审查和方案审查补充模板与输出结构。
3. 在主链中加入“未通过需求/方案审查不可进入 implement”的门禁。

验证点：

1. 新需求能被 reviewer 在实现前阻断。
2. reviewer 的结论能直接指向具体文档修订位置。

### Phase 2：project-agent 升级为项目 steward

目标：

1. `project-agent` 成为项目画像、规划、第三方来源和项目记忆的 owner。
2. 明确它“负责维护事实源，不直接写业务代码”的边界。

实施步骤：

1. 定义项目画像模板：项目介绍、模块边界、入口、部署、API、规划。
2. 为 `project-agent` 补充维护动作：更新 PRD、更新架构设计、维护 API registry、回写决策。
3. 打通与 `reviewer`、`web-agent` 的协作链路。

验证点：

1. 任一活跃项目都能由 `project-agent` 输出项目画像与 API 来源。
2. 用户追问“这个项目现在逻辑是什么样”时，不再依赖散落上下文。

### Phase 3：项目级记忆模块落地

目标：

1. 把项目长期上下文从全局 `MEMORY.md` 分离出来。
2. 为每个项目建立独立记忆模块。

实施步骤：

1. 确认项目记忆目录结构与字段契约。
2. 决定首版存储方案：
   - 本地 `Markdown + JSON`
   - 可选接入官方 Honcho Memory
3. 建立项目摘要注入策略和更新策略。

验证点：

1. 项目切换时能按项目注入不同上下文。
2. 项目级事实不再污染全局记忆。

### Phase 4：第三方 API watch 收口

目标：

1. 只对项目声明过的第三方依赖做 watch。
2. 建立 `官方 docs / changelog / repo / SDK` 的单一来源表。

实施步骤：

1. 定义 `API_REGISTRY.json` 与 `SOURCE_REGISTRY.json` 契约。
2. 为 `project-agent` 增加维护入口。
3. 为 watcher 增加“变更记录 -> 项目修订任务”的回流。

验证点：

1. 变更记录能精确落到具体项目。
2. 不再出现全局泛化 web 扫描消耗大量 token 的情况。

### Phase 5：默认 cron / job 基线裁剪

目标：

1. 退出默认主链的自进化任务。
2. 保留任务执行、最小巡检、项目维护与交付核心链。

实施步骤：

1. 列出当前 repo 模板和 runtime 现值差异。
2. 标记：
   - 保留
   - 降级为手动/低频
   - 删除
3. 同步更新文档和安装器默认 profile。

验证点：

1. 默认 job 数量显著减少。
2. 核心交付链仍可稳定运行。
3. 自进化退出后，不影响项目交付质量。

## 4. 风险与回滚

### 4.1 主要风险

1. reviewer 前移后，流程可能变慢。
2. project-agent 升级后，事实源维护成本会上升。
3. cron 裁剪过度，可能误删仍有价值的运维能力。
4. 项目记忆模块设计不当，可能造成新的双真相源问题。

### 4.2 防御策略

1. 先以文档和 dry-run 落地，再切 runtime 默认值。
2. 先建立“保留 / 降级 / 删除”清单，再动 job 安装器。
3. 项目记忆首版只做最小字段，不一次性扩张。
4. 保留手动入口，避免因为默认裁剪导致能力完全消失。

## 5. 验收清单

1. `reviewer` 有明确的需求审查与方案审查入口。
2. `project-agent` 能输出项目画像和 API 来源。
3. 项目级记忆目录能够按项目独立存在。
4. 第三方 API watch 只针对项目声明过的来源运行。
5. 默认 cron 基线从“自进化优先”切到“项目交付优先”。

## 6. 当前裁决

本轮只完成 Phase 0 文档落盘，不执行任何 runtime 改动。
