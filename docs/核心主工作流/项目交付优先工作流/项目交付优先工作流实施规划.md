# 项目交付优先工作流实施规划

## 目标

把通用软件交付过程收敛为可配置、可验证、可回流、可发布的状态机，消除对固定项目、行业、主机和服务拓扑的依赖。

## Phase 1：需求与上下文

- 维护唯一需求包和结构化验收条件。
- 读取仓库规则、项目记忆、源码和测试。
- 将只读来源与必改目标分开。
- 由独立 reviewer 审核需求遗漏和冲突。

验收：`requirements.md` 和审查产物可独立解释范围、非目标与通过标准。

## Phase 2：结构化方案

- 生成 `delivery_plan.json`。
- 明确任务切片、目标文件、实施步骤、验证命令、部署条件、回滚和人工阻塞条件。
- 禁止按历史项目关键词隐式增加目标文件。

验收：方案可由机器校验，且人类文档只从同一契约渲染。

## Phase 3：隔离实现

- 每个实现角色获得独立工作区。
- 只允许修改计划中的目标范围。
- 保存命令记录、补丁和变更摘要。

验收：目标仓库原有未提交修改不被覆盖，补丁可独立审阅和重放。

## Phase 4：验证与审查

- 执行项目声明的定向测试和静态检查。
- 将退出码、输出与失败摘要写入验证报告。
- 由独立 reviewer 检查正确性、回归风险、测试充分性和需求覆盖。
- 失败只回流到对应阶段。

验收：成功结论可由测试产物和审查产物共同证明。

## Phase 5：部署与验收

- 部署阶段默认关闭。
- 仅在需求明确提出、调用方提供命令且显式许可时运行。
- 烟测命令可重复配置，并保存每条命令的证据。
- 回滚命令与触发条件属于交付计划的一部分。

验收：没有项目专属服务名、端口或进程控制逻辑进入通用执行器。

## Phase 6：知识写回与 Git 发布

- 只写回稳定事实、决策、失败经验和验证口径。
- 运行日志与会话转录保留在运行目录，不进入仓库。
- 发布仅包含已验收文件；推送后回读远端 SHA。

验收：本地提交、远端分支和交付证据一致，暂存区不含缓存、凭证或范围外文件。

## 回归矩阵

| 能力 | 覆盖 |
| --- | --- |
| 路径与环境注入 | Windows、Linux 风格临时目录 |
| 计划编译 | 通用 API、CLI、文档与配置需求 |
| 失败回流 | 需求、方案、实现、验证、审查、部署、发布 |
| 部署门禁 | 未要求、明确要求、缺少命令、烟测失败 |
| Git 边界 | 混合工作树、隔离补丁、暂存扫描、远端回读 |
| 数据卫生 | 会话、缓存、机器路径和敏感值均不跟踪 |

## 完成定义

1. 核心代码无固定项目和行业专用分支。
2. Profile、命令、目录和连接器可配置。
3. 定向测试与仓库静态检查全部通过。
4. README、需求、变更记录和运行手册保持一致。
5. 提交已推送并完成远端 SHA 回读。
