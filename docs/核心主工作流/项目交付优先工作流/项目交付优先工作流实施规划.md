# 项目交付优先工作流 — 实施规划

> 版本：v0.5 | 2026-04-27（补齐 Task Center 待办持续推进）
> 架构设计：[项目交付优先工作流架构设计.md](项目交付优先工作流架构设计.md)

## 1. 实施目标

把默认工作流从"自动进化优先"调整为"编码交付优先"，核心落地以下能力：

1. 自动探索需求——读取项目事实源、运行态证据、外部官方资料和成熟方案。
2. 需求包与方案包生成——把聊天需求转为可执行、可审查、可验收的交付输入。
3. 双 AI 对抗式审查——2 个 AI 互相探讨，覆盖需求、方案、代码三阶段。
4. 编码执行编排——调用 HardFlow Core / ACP 编码链，禁止实现者脱离已审查方案自由发挥。
5. 测试与验收编排——统一收集 lint、typecheck、unit、integration、smoke、部署验证和验收证据。
6. 失败学习 → 文档回写——模型做不好的任务，分析根因后修改文档纠偏。
7. project-agent 升级为项目维护 owner，不同项目有独立记忆模块。
8. 第三方 API 定期更新，随时保持最新。
9. 自进化完全移除，不保留为可选。

## 4. 风险与回滚

### 4.1 主要风险

1. 双 AI 审查增加 token 消耗和延迟。
2. project-agent 升级后，事实源维护成本会上升。
3. 自进化完全移除后，需要人工决定何时做系统改进。
4. 项目记忆模块设计不当，可能造成新的双真相源问题。
5. 端到端流水线如果只做文档约束，不做状态机，会继续退化成“靠聊天记住流程”。
6. 宿主兼容如果散落在业务步骤里，会产生多套不可维护的流程。

### 4.2 防御策略

1. 先以文档和 dry-run 落地，再切 runtime 默认值。
2. 双 AI 审查对简单任务可用轻量模式（A 审查后 B 只做关键点抽查）。
3. 项目记忆首版只做最小字段，不一次性扩张。
4. 项目记忆与蒸馏热记忆的边界已在架构设计 5.3 和记忆蒸馏实施规划 1.3 中双向裁决。
5. 自进化移除后，系统改进由用户按需触发，不自动执行。
6. Phase 6 必须实现 `Coding Pipeline Run` 状态机，不能只新增 prompt 或 README。
7. 宿主兼容必须集中在 runtime adapter，不允许在需求、方案、编码、测试阶段复制两套分支。

## 5. 验收清单

1. 新功能的第一反应是查项目事实源和网上成熟方案。
2. 每个需求都有 `Coding Pipeline Run` 记录，能看到状态、产物、失败原因和下一步。
3. 每次审查有 2 个 AI 互相探讨的记录，不是单 AI 走过场。
4. 编码交付必须经过需求审查、方案审查、编码、测试、代码审查、验收、回写。
5. 模型反复失败时，需求文档被主动修改以纠偏。
6. `project-agent` 能输出项目画像和 API 来源。
7. 项目级记忆目录能够按项目独立存在。
8. 第三方 API watch 只针对已声明来源运行，定期更新。
9. 默认 cron 中完全没有自进化任务。
10. 同一流水线可在任意显式 `runtime-home` 下 dry-run 通过；OpenClaw / Hermes 只是预设场景。
