# 项目交付优先工作流 — 实施规划

> 版本：v0.3 | 2026-04-22（集成双 AI 对抗审查 + 失败学习回写）
> 架构设计：[项目交付优先工作流架构设计.md](项目交付优先工作流架构设计.md)

## 1. 实施目标

把默认工作流从"自动进化优先"调整为"项目交付优先"，核心落地以下能力：

1. 检索是第一反应——不允许跳过检索直接动手。
2. 双 AI 对抗式审查——2 个 AI 互相探讨，覆盖需求、方案、代码三阶段。
3. 失败学习 → 文档回写——模型做不好的任务，分析根因后修改文档纠偏。
4. project-agent 升级为项目维护 owner，不同项目有独立记忆模块。
5. 第三方 API 定期更新，随时保持最新。
6. 自进化完全移除，不保留为可选。

### Phase 1：双 AI 对抗式审查落地

目标：

1. 把 reviewer 从单 AI 审查升级为双 AI 对抗式审查。
2. 覆盖需求审查、方案审查、代码审查三个阶段。
3. 建立对抗式审查的统一输出契约和共识规则。
4. 让审查结果能回写需求文档和实施规划。

新增/修改文件：

| 文件 | 动作 | 说明 |
|------|------|------|
| `skills/library/dual-ai-review/SKILL.md` | 新增 | 双 AI 对抗式审查 Skill（主 Skill） |
| `skills/library/dual-ai-review/templates/requirements_review.md` | 新增 | 需求审查输出模板（含 A/B 独立意见 + 联合结论） |
| `skills/library/dual-ai-review/templates/solution_review.md` | 新增 | 方案审查输出模板 |
| `skills/library/dual-ai-review/templates/code_review.md` | 新增 | 代码审查输出模板 |
| `skills/library/dual-ai-review/references/review-gate-contract.md` | 新增 | 对抗审查与 G0-G6 门禁的映射契约 |
| `skills/library/dual-ai-review/references/consensus-rules.md` | 新增 | 共识规则（最多 3 轮、分歧上报、中止条件） |
| `scripts/openclaw-ops/policy/review_gate_enforcer.py` | 新增 | 审查门禁执行器（检查联合结论后放行 G0） |

实施步骤：

1. 设计双 AI 对抗审查的 prompt 结构：A 独立审查 → B 质疑 → 共识讨论 → 联合结论
2. 设计需求审查模板：范围、边界、验收、外部来源引用检查项、A/B 意见区
3. 设计方案审查模板：技术路径、依赖选择、模型使用合理性、B 必须挑战的质疑项
4. 设计代码审查模板：是否按预定规则执行、偏差记录、上溯建议
5. 定义统一输出 schema（含 A/B 独立意见 + 联合裁决 + 分歧记录）
6. 实现 `review_gate_enforcer.py`：读取联合结论 → 判断是否允许进入 G0
7. 修改 HardFlow 主链（`hardflow_runner.py`），在 G0 之前检查 reviewer gate

验证点：

1. 审查产物中能看到 A 和 B 的独立意见和联合结论
2. A 和 B 意见冲突时，最多 3 轮讨论后标记分歧上报用户
3. `requires_revision` 联合结论后，HardFlow G0 被自动阻断

1. 当模型反复失败时，分析根因并回写到文档。

| `scripts/openclaw-ops/policy/failure_tracker.py` | 新增 | 失败次数跟踪器（触发条件检测） |

实施步骤：

1. 定义失败记录的数据格式（任务类型、失败次数、根因分类、AI 模型、时间戳）
2. 实现 `failure_tracker.py`：跟踪同类任务失败次数，触发条件达到时产出告警
3. 设计 `failure_analysis.md` 模板：根因分类 → 网上查方案 → 回写目标 → 纠偏措施
4. 在双 AI 审查流程中增加"历史失败查询"步骤（B 必须检查历史记录）
5. 建立回写到需求文档/方案文档/模型执行规约的标准化路径

验证点：

1. 同一类任务连续 2 次失败后触发失败学习流程
2. 失败分析产物中有明确的根因分类和回写目标
3. 回写后的文档在下次执行时被正确加载

## 4. 风险与回滚

### 4.1 主要风险

1. 双 AI 审查增加 token 消耗和延迟。
2. project-agent 升级后，事实源维护成本会上升。
3. 自进化完全移除后，需要人工决定何时做系统改进。
4. 项目记忆模块设计不当，可能造成新的双真相源问题。

### 4.2 防御策略

1. 先以文档和 dry-run 落地，再切 runtime 默认值。
2. 双 AI 审查对简单任务可用轻量模式（A 审查后 B 只做关键点抽查）。
3. 项目记忆首版只做最小字段，不一次性扩张。
4. 项目记忆与蒸馏热记忆的边界已在架构设计 5.3 和记忆蒸馏实施规划 1.3 中双向裁决。
5. 自进化移除后，系统改进由用户按需触发，不自动执行。

## 5. 验收清单

1. 每次审查有 2 个 AI 互相探讨的记录，不是单 AI 走过场。
2. 模型反复失败时，需求文档被主动修改以纠偏。
3. `project-agent` 能输出项目画像和 API 来源。
4. 项目级记忆目录能够按项目独立存在。
5. 第三方 API watch 只针对已声明来源运行，定期更新。
6. 默认 cron 中完全没有自进化任务。
7. 新功能的第一反应是查网上成熟方案。

## 6. 当前裁决

本轮只完成 Phase 0 文档落盘，不执行任何 runtime 改动。
