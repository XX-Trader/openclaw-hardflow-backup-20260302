# OpenClaw 官方上游接入最小方案（2026-03-06）

## 目标

- 直接复用 OpenClaw 官方稳定版本，减少重复开发和维护成本。
- 保留当前项目的业务定制能力，同时避免“深度绑定主干”导致升级困难。

## 成功标准

- 官方代码在 `vendor/` 独立管理，不与本地业务代码混写。
- 本地改动只在桥接层与补丁层，升级时可定位、可回滚。
- 有统一命令完成初始化、升级、状态检查。

## 运行时边界（Task 1 冻结）

- 唯一官方运行时根目录固定为 `vendor/openclaw-official/`，本仓不再把自己视为 OpenClaw 主程序仓库。
- 仓库内的 `openclaw/openclaw.json` 只承担 workflow overlay 配置源职责；实际 runtime 配置落点仍是 `~/.openclaw/openclaw.json`。
- `scripts/openclaw-ops/install_workflow_profile.py` 负责把 overlay 配置合并写入 runtime 配置，并继续安装业务任务；它不复制、不改写 `vendor/openclaw-official/` 核心代码。
- 运行时边界的详细约束见 `integration/openclaw-bridge/runtime-boundary.md`。

## 目录约定

```text
vendor/
  openclaw-official/            # 官方源码（submodule 或 subtree）
integration/
  openclaw-bridge/              # 本地桥接层（只对外暴露稳定接口）
patches/
  openclaw/                     # 必须改官方代码时的补丁记录
.workflow/
  openclaw-upstream-binding.json  # 上游绑定配置（由脚本生成）
```

## 引入方式（推荐 submodule）

当前仓库已完成首次接入，绑定目标：

- 官方仓库：`https://github.com/openclaw/openclaw.git`
- 固定版本：`v2026.3.2`

1. 初始化（固定到稳定 tag/release）：

```bash
python skills/library/openclaw-workflow-manager/scripts/openclaw_upstream_binding.py init \
  --strategy submodule \
  --repo-url https://github.com/openclaw/openclaw.git \
  --ref <稳定tag> \
  --vendor-dir vendor/openclaw-official
```

2. 查看状态：

```bash
python skills/library/openclaw-workflow-manager/scripts/openclaw_upstream_binding.py status
```

3. 升级到新稳定版本：

```bash
python skills/library/openclaw-workflow-manager/scripts/openclaw_upstream_binding.py update \
  --ref <新稳定tag>
```

## 升级策略

- 不跟 `main`，只跟稳定 `tag/release`。
- 建议月度升级节奏：
  - 拉取新 tag
  - 运行核心流程回归
  - 检查桥接层兼容性
  - 确认后再合并

## 边界规则

- 禁止在 `vendor/openclaw-official/` 直接做业务改动。
- 如确需修改官方代码：
  - 先在 `patches/openclaw/` 记录补丁原因、影响范围和回滚方式
  - 优先将改动沉淀到 `integration/openclaw-bridge/`
- 本地 overlay 仅允许通过配置、cron、hooks、plugins、skills 和 bridge 文档影响运行时。
- 任何“复制官方源码到 `~/.openclaw`”的做法都视为 legacy，不再作为默认安装路径。

## 回滚策略

- submodule 回滚：把 submodule 指针回退到上一个稳定提交即可。
- subtree 回滚：回滚对应 subtree merge commit。

## 风险与取舍

- 使用 submodule 会增加一次拉子模块步骤，但升级边界最清晰。
- 使用 subtree 对下游更“无感”，但历史更重、回滚和审计成本更高。
- 当前方案默认 submodule，必要时可切换 subtree。

## 2026-03-06 收敛补充（Task 2-6）

### Task 2：Cron 收口到官方 surface

- `cron/jobs.json` 继续作为业务任务定义源。
- 安装脚本只负责生成/更新 job payload。
- 运行时状态与手工触发统一走官方 CLI：

```bash
openclaw cron status --json
openclaw cron run <job-id> --force
openclaw cron runs --id <job-id> --limit 20
```

- `legacy optimize_*` 链路继续标记为 legacy，本轮不做大迁移，只通过 `--legacy-optimize-jobs-mode disable` 收敛生产主链。

### Task 3：Hooks 收口到官方 loader

- 仓库 `hooks/` 目录不再通过手工散落复制进入运行时。
- `install_workflow_profile.py` 在合并 overlay 时动态写入：
  - `hooks.internal.entries.*`
  - `hooks.internal.load.extraDirs += <repo>/hooks`
- 开发态如需显式 link，按 `integration/openclaw-bridge/hooks-install.md` 使用 `openclaw hooks install -l <hook-dir>`。

### Task 4：治理继续留在 Python

- `policy_enforcer.py`
- `task_center.py`
- `project_index_maintainer.py`
- `task_executor_runner.py`

这些脚本继续作为业务治理层，不迁入官方核心。

桥接入口约束：

- 官方 `cron`
- 官方 `hooks`
- 官方 `gateway/webhook`

输出契约约束：

- JSON 机器输出
- `NO_REPLY` 静默成功输出

### Task 5：Channel / Plugin / Skills 回到官方表面

- Telegram 配置继续走 `channels.telegram`。
- Telegram 插件继续走 `plugins.entries.telegram`。
- 仓库 `skills/` 目录通过 `skills.load.extraDirs` 注入官方 skills loader。
- overlay 只保留业务配置包装，不再承担通道/插件/skills 生命周期实现。

### Task 6：补验收与 legacy 标记

验收清单见：

- `integration/openclaw-bridge/acceptance-checklist.md`

额外规则：

- `sync_openclaw_ops_files.py` 只同步 `ops/`。
- 任何“复制官方源码到运行时目录”的流程都视为 legacy。
- `git diff -- vendor/openclaw-official` 必须保持为空。
