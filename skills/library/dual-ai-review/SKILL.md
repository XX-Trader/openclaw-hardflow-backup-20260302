# 双 AI 对抗式审查 — 操作手册

## 1. 何时使用

- 新需求进入实现前，必须进行**需求审查**
- 架构设计/实施规划完成后，必须进行**方案审查**
- 代码实现完成后，必须进行**代码审查**
- 任何审查阶段，**不允许单 AI 独立完成**

## 2. 不适用场景

- 纯格式检查（如 JSON Schema 校验）→ 用自动化工具
- 已明确的小 bug 修复（如拼写错误）→ 直接修复，不触发完整对抗审查
- 自进化相关任务 → 本项目已移除自进化

## 3. 核心原则

### 3.1 为什么必须双 AI

单个 AI 审查容易走过场——它倾向于认为自己的方案是对的。2 个 AI 互相质疑，能发现单模型的盲点。

**铁律**：任何审查产物如果只看到一个 AI 的意见，视为无效，必须驳回重审。

### 3.2 模型选择策略

| 审查阶段 | Reviewer-A（主审） | Reviewer-B（对抗） | 理由 |
|---------|-------------------|-------------------|------|
| 需求审查 | gpt-5.4 | glm-4.7 / Doubao-Seed | A 强推理，B 不同视角 |
| 方案审查 | gpt-5.4 | Claude Opus / Doubao-Seed | A 架构能力，B 挑刺 |
| 代码审查 | gpt-5.3-codex | gpt-5.4 | A 代码专长，B 全局审视 |

**模型隔离原则**：A 和 B 必须是不同模型或同模型的完全独立上下文，B 在给出自己的独立意见前**不允许看到 A 的意见**。

### 3.3 对抗流程

```text
Round 0: coordinator 提交审查材料 + 背景上下文
    │
Round 1: Reviewer-A 独立审查，产出初始意见（B 不可见）
    │
Round 2: Reviewer-B 独立审查 + 看到 A 的意见后质疑
    │         B 必须回答：A 漏掉了什么？A 的结论哪里有问题？
    │
Round 3: Reviewer-A 看到 B 的质疑后，选择：
    │         - 接受质疑，修正结论
    │         - 坚持原结论，给出更强证据
    │         - 提出折中方案
    │
Round 4（如需要）: Reviewer-B 对 A 的回应再次评估
    │
    ▼ 终止条件
    ├─ 双方共识 → 输出联合结论
    ├─ 3 轮未收敛 → 标记分歧，上报 coordinator 转人工裁决
    └─ 任一方发现"方向性错误" → 立即中止，不浪费 token
```

### 3.4 共识规则

1. **双方同意** → 直接通过/驳回
2. **一方同意、一方反对** → 最多再讨论 2 轮（总共 3 轮），仍无共识 → 标记分歧
3. **任一方发现方向性错误**（如 XY 问题、技术路线完全错误）→ 立即中止，返回 `blocked_by_unknowns`
4. **分歧上报** → 必须附带 A 和 B 的完整意见，不能由某一方擅自裁决

## 4. 三阶段审查模板

### 4.1 需求审查

使用模板：`templates/requirements_review.md`

审查焦点：
- 外部来源检索报告是否存在且充分（检索是第一反应）
- 需求边界、成功标准、非目标是否明确
- 是否存在 XY 问题
- 是否缺少第三方 API 限制、兼容边界

### 4.2 方案审查

使用模板：`templates/solution_review.md`

审查焦点：
- 技术方案是否复用现有成熟能力
- 模型/工具选择是否合理（查询历史失败记录）
- 是否应该优先官方方案而非自研
- 复杂度是否过高

**B 必须挑战的质疑项**：
- "用这个模型做这件事"是否真的合适？
- "自研这个组件"是否合理？网上有没有成熟轮子？
- 有没有更简单的路径？

### 4.3 代码审查

使用模板：`templates/code_review.md`

审查焦点：
- 代码是否按预定方案和规则执行（不是"能跑就行"）
- 是否补齐 API 文档、测试、验收产物
- 是否出现"代码能跑，但偏离预定规则"
- 发现的问题是否应上溯到需求/方案文档

## 5. 输出契约

### 5.1 审查产物存放路径

```
.workflow/reviews/<task_id>/
├── requirements_review.md      # 需求审查产物（如适用）
├── solution_review.md          # 方案审查产物（如适用）
├── code_review.md              # 代码审查产物（如适用）
├── consensus.md                # 联合结论摘要
└── dissent.md                  # 分歧记录（如有）
```

### 5.2 联合结论格式

每份审查产物必须包含：

```markdown
## Reviewer-A 独立意见
- 结论：pass / reject / need_more_info
- 关键发现：...
- 风险等级：P0 / P1 / P2 / P3

## Reviewer-B 独立意见
- 结论：pass / reject / need_more_info
- 关键发现：...
- 对 A 的质疑：...

## 共识讨论记录
- Round 1: ...
- Round 2: ...
- Round 3: ...

## 联合结论
- 最终裁决：ready_for_solution / ready_for_implement / requires_revision / blocked_by_unknowns
- 置信度：high / medium / low
- 分歧标记：有 / 无
- 回写建议：...
```

### 5.3 门禁信号

审查结论直接决定 HardFlow 门禁：

| 联合结论 | 含义 | 后续动作 |
|---------|------|----------|
| `ready_for_solution` | 需求审查通过，可以进入方案设计 | 进入方案审查 |
| `ready_for_implement` | 方案审查通过，可以进入编码 | 进入 HardFlow G0 |
| `requires_revision` | 需要修改后重新审查 | 回写文档 → 修改 → 重新触发审查 |
| `blocked_by_unknowns` | 关键信息缺失，无法判断 | 暂停，要求补充信息 |

## 6. 与 HardFlow G0-G6 的映射

```text
双AI需求审查 ──ready_for_solution──► 双AI方案审查 ──ready_for_implement──► G0(需求包检查)
                                                                            │
                                                                            ▼
                                                                      G1-G3(编码)
                                                                            │
                                                                            ▼
                                                                      G4(安全扫描)
                                                                            │
                                                                            ▼
双AI代码审查 ◄────────────── 代码完成 ◄─────────────────────────────────────┘
    │
    ▼
G5-G6(验收)
```

**关键裁决**：
- `ready_for_implement` 是 G0 的前置条件，没有联合结论不允许进入 G0
- 双 AI 审查检查的是**业务合理性**，G0 检查的是**格式完整性**，互不替代

## 7. 失败学习接口

当审查中发现以下情况时，触发失败学习流程：

1. 同类任务连续 2 次未通过审查
2. B 指出"这个模型/流程历史上多次在此类任务上失败"
3. 用户主动反馈"这块总是做不好"

触发后：
- 在审查产物中增加 `failure_learning_triggered: true` 标记
- 输出 `failure_analysis.md`（使用 failure-learning Skill 模板）
- **必须上报用户确认后才能回写文档**

## 8. 评分与问责

| 指标 | 计算方式 |
|------|----------|
| 审查覆盖率 | 实际触发双 AI 审查的任务数 / 应触发任务数 |
| 分歧率 | 产生分歧的任务数 / 总审查任务数 |
| 回写率 | 审查导致文档回写的次数 / 总审查任务数 |
| 漏检率 | 审查通过后仍出现重大问题的次数 / 总通过任务数 |

**问责**：漏检率 > 5% 时，必须审查 reviewer 的 prompt 和模型配置。
