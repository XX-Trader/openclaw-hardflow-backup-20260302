# PUA 排障方法论

> 来源: [tanweai/pua](https://github.com/tanweai/pua) v3 — 适配 HardFlow 工作流

## 何时触发

- 连续失败 2 次及以上
- 排查方向不明、原地打转
- 需要系统性分析复杂问题
- 修复后需要确保完整闭环

---

## 一、5 步通用方法论（每次失败或卡壳后执行）

### Step 1: 闻味道 — 诊断卡壳模式

停下来。列出所有尝试过的方案，找共同模式。如果你一直在做同一思路的微调（换参数、换措辞、改格式），你就是在原地打转。

**自问**：
- 我是在换方案，还是在微调同一个方案？
- 这些尝试有本质区别吗？

### Step 2: 揪头发 — 拉高视角（5 个维度，跳过任何一个 = 不合格）

1. **逐字读失败信号** — 错误信息、拒绝原因、空结果——不是扫一眼，是逐字读。
2. **主动搜索** — 不要靠记忆和猜测——搜索完整报错信息、官方文档、GitHub Issues。
3. **读原始材料** — 不是读摘要或你的记忆，是读原始来源：出错文件上下文 50 行、官方文档原文。
4. **验证前置假设** — 你假设成立的所有条件，哪个没有用工具验证过？版本、路径、权限、依赖——全部确认。
5. **反转假设** — 如果你一直假设"问题在 A"，现在假设"问题不在 A"，从对立方向重查。

> ⚠️ 维度 1-4 完成前不允许向用户提问（铁律二：先做后问）。

### Step 3: 照镜子 — 自检

- 是否在重复同一思路的变体？
- 是否只看了表面症状，没找根因？
- 是否该搜索却没搜？该读文件/文档却没读？
- 是否检查了最简单的可能性？（错别字、格式、前提条件）

### Step 4: 执行新方案

每个新方案必须满足三个条件：
- 和之前的方案**本质不同**（不是参数微调）
- 有明确的**验证标准**
- 失败时能产生**新信息**

### Step 5: 复盘

- 哪个方案解决了？为什么之前没想到？还剩什么未试？
- **主动延伸**：问题解决后不要停。检查同类问题是否存在、修复是否完整、是否有可以预防的措施。

## 二、7 项检查清单（L3+ 连续失败 4 次强制完成）

连续失败 4 次及以上时，必须逐项完成并汇报：

- [ ] **读失败信号**：逐字读完了吗？
- [ ] **主动搜索**：用工具搜索过核心问题了吗？
- [ ] **读原始材料**：读过失败位置的原始上下文了吗？
- [ ] **验证前置假设**：所有假设都用工具确认了吗？
- [ ] **反转假设**：试过与当前方向完全相反的假设吗？
- [ ] **最小隔离**：能在最小范围内隔离/复现这个问题吗？
- [ ] **换方向**：换过工具、方法、角度、技术栈、框架吗？（不是换参数——是换思路）

## 三、方法论自动路由（按任务类型选择策略）

收到任务后，先识别任务类型，选择最匹配的方法论：

| 任务类型 | 信号关键词 | 核心方法 |
|---------|-----------|---------|
| **Debug/Fix** | error, bug, fix, crash, 报错 | 根因分析 5-Why + 反转假设 + 蓝军自攻击 |
| **Build New** | add, create, build, implement, 新增 | 先质疑需求 → 删减 → 简化 → 加速 → 自动化 |
| **Code Review** | review, refactor, 质量, 重构 | 减法思维 + DRI + 安全/性能/架构三维审核 |
| **Research** | research, search, find, 调研 | 穷尽搜索再下判断，不靠猜测 |
| **Architecture** | design, architecture, 架构, 方案 | 逆向工作法（从期望结果倒推） + 6-Pager 严谨逻辑 |
| **Performance** | performance, slow, optimize, 性能 | A/B 测试一切，数据驱动，不靠直觉 |
| **Deploy/Ops** | deploy, config, 部署, 上线 | 前置检查 → 执行留痕 → 验证闭环 → 回滚就绪 |
| **Testing** | test, verify, 验证, 测试 | 端到端闭环 + 边界覆盖 + 证据优先 |

**输出选择标签**：识别后在回复开头输出：
```
[方法论路由 🧭] 检测到 Debug 任务 → 选择根因分析 5-Why + 蓝军自攻击
```

## 四、失败梯度升级（压力自动升级）

| 连续失败次数 | 等级 | 强制动作 |
|------------|------|---------|
| 第 2 次 | **L1** | 停下，切换**本质不同**的方案（不是改参数） |
| 第 3 次 | **L2** | 搜索完整错误 + 读源码上下文 50 行 + 列 3 个不同假设 |
| 第 4 次 | **L3** | 完成上方 **7 项检查清单**（全部），列出 3 个全新假设并逐个验证 |
| 第 5 次+ | **L4** | 最小 PoC + 隔离环境 + 完全不同的技术栈。若仍未解决 → 结构化失败报告 |

---

## 五、结构化失败报告（体面的退出）

7 项检查清单全部完成、且仍未解决时，输出结构化失败报告：

1. **已验证的事实**（7 项清单的结果）
2. **已排除的可能性**（附每条排除的依据）
3. **缩小后的问题范围**
4. **推荐的下一步方向**
5. **可供下一个接手者使用的交接信息**

> 这不是"我不行"。这是"问题的边界在这里，这是我移交给你的一切"。

---

## 六、主动出击清单（每次修复/实现后强制自检）

完成任何修复或实现后，必须过一遍：

- [ ] 修复是否经过验证？（运行测试、curl 验证、实际执行）
- [ ] 改了代码？build 一下。改了配置？重启看生效没。写了 API？curl 看返回值。
- [ ] 同文件/同模块是否有类似问题？
- [ ] 上下游依赖是否受影响？
- [ ] 是否有边界情况没覆盖？
- [ ] 是否有更好的方案被我忽略了？
- [ ] 如果用户没有明确说的部分，我是否主动补充了？
